What Design Decisions Went into this Process? • Name Node (in earlier versions of the HDFS) is a singleton (there is only one), so can be overloaded • Minimise client contact with the Name Node (only do a single request) • Data is replicated in multiple places , some may be closer (with regard to network latency) than others • Select the closest one , via Rack Awareness • Rack structure is manually configured in a file in the HDFS, not dynamically tracked https://data - flair.training/blogs/rack - awareness - hadoop - hdfs/


<!-- Page 10 -->

What other options might there have been? • When the Client decides which data node to write? • Contact all replicas, return when the first responds • Should have fastest read time , but involves redundant requests (expending disk read and network resources) • Contact a replica chosen uniformly at random so as to balance the load • Would have slightly longer latency , but might work better when the cluster is heavily loaded with requests • Contact the replica that is least loaded (and has the data) • Like the above , but requires nodes to report their load somehow (and which may change rapidly) • As you can see, there was choice made here by the HDFS designers , where they wanted data locality, but wanted to minimise resource usage and avoid continually tracking how busy each data node is

Pipelining • To be clear, multiple block packets can be ‘in - flight’ at the same time • Acknowledgements are returned when a packet is received • hFlush will be periodically called to write packets to the journal, in case system failure occurs Client Data Node Data Node Data Node t0 t1 ACK

What Design Decisions Went into this Process? • Again the Name Node is a bottleneck • Only contact it once • We don’t know how fast or congested the network is • Have the Client send the data only once • Have each Data Node forward what data it receives on to the next • We want to maximise transfer rates • Send packets in parallel • Data Nodes can be sending and receiving at the same time • We need to know when the block is available • Have the Data Node report directly to the Name Node once it has a whole block


<!-- Page 23 -->

What other options might there have been? • Client could have sent data to all data nodes simultaneously • Would have decreased the time until all nodes have the data , but might saturate the network connection on the client • Client contacts all replicas one after the other • Spreads network traffic out over time , but takes longer • Client sends data to first replica, then those forward to remaining replicas lazily (i.e., when idle) • Avoids overloading individual data nodes , but may take a long time before full replication is achieved
