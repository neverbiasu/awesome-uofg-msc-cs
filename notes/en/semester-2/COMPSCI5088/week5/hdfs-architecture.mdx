HDFS is a user-space distributed file system designed to run on commodity hardware.

## HDFS Architecture

HDFS follows a **Master/Slave** architecture.

![HDFS Architecture](/images/COMPSCI5088/week5/05-04-HDFS-004.png)

### Components
- **NameNode (Master)**: Stores metadata (file names, permissions, block locations). It manages the file system namespace.
    - **Single Point of Failure (SPOF)**: Traditionally a weakness, mitigated by Secondary NameNode and High Availability (HA) setups.
- **DataNode (Slave)**: Stores the actual data blocks. Periodically sends **Heartbeats** and **BlockReports** to the NameNode.
- **Client**: Interacts with NameNode for metadata and DataNodes for I/O.

### Blocks & Replication
- **Block Size**: Default is 128MB (large size to minimize seek time).
- **Replication Factor**: Default is 3.
    - 1st Replica: Local node.
    - 2nd Replica: Different rack.
    - 3rd Replica: Same rack as 2nd, different node.

![HDFS Replication](/images/COMPSCI5088/week5/05-04-HDFS-007.png)

## HDFS Operations

### Read Process
1.  Client asks NameNode for file location.
2.  NameNode returns list of DataNodes holding blocks.
3.  Client reads blocks directly from closest DataNodes.

![HDFS Read](/images/COMPSCI5088/week5/05-05-HDFS2-004.png)

### Write Process (Pipeline)
1.  Client asks NameNode to create file.
2.  NameNode checks permissions and returns DataNodes for the first block.
3.  Client writes data to the first DataNode.
4.  First DataNode forwards to the second, second to the third (Pipeline).
5.  All acknowledge success before moving to the next block.

![HDFS Write](/images/COMPSCI5088/week5/05-05-HDFS2-008.png)

## Key Takeaway

- **Write-Once-Read-Many (WORM)**: HDFS is optimized for batch processing, not random updates.
- **Data Locality**: Moving computation to the data (MapReduce/Spark) is cheaper than moving petabytes of data.
- **Fault Tolerance**: Handled automatically via replication and heartbeats.
