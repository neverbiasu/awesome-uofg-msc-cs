## Overview
- **Goal**: Understand how systems identify users and determine their resource access rights.
- **Scope**: Covers the complete process from Authentication to Authorization, and model selection for different security needs.

## Learning Objectives
1. Distinguish between the concepts and responsibilities of **Authentication** and **Authorization**.
2. Understand the lifecycle of digital identity and common authentication methods (Passwords, OTP, Biometrics).
3. Analyze and select appropriate authorization models: DAC, RBAC, ABAC, or MAC.
4. Master the principles of OTP generation and verification using Python.

## Key Knowledge Points

### 1. Access Control Basics

![Access Control Workflow](/images/COMPSCI5104/week3/SSE-Lecture3-006.png)

![Access Control System](/images/COMPSCI5104/week3/SSE-Lecture3-007.png)
- **Definition**: Access control is the process of identifying user credentials, verifying their identity, and authorizing their access to specific resources.
- **Core Workflow**:
  1. **User**: The subject requesting access to resources.
  2. **Authentication Mechanism**: Verifies user identity (e.g., login).
  3. **System Administrator**: Manages the permissions database.
  4. **Authorization Database**: Stores user permissions and access rules.
  5. **Access Control**: Decides whether to allow access based on identity and rules.
  6. **System Resources**: The files, data, or applications ultimately being accessed.

- **Key Distinction**:
  - **Authentication**: Who you are? / Are you allowed to use the system?
  - **Authorization**: What can you do? / Do you have the right to access a specific resource?

---

### 2. Digital Identity Lifecycle
- **Definition**: Digital identity is a set of attributes that uniquely identifies a user or entity (e.g., username, biometrics, PINs).
- **Lifecycle**:
  1. **Enrolment**: Initial capture of identity, collecting PII (Personally Identifiable Information), setting up credentials.
  2. **Maintenance**: Updating information, changing passwords, refreshing biometric data.
  3. **Deactivation/Deletion**: Temporarily or permanently removing identity (e.g., resignation, privacy requests).

### 3. Authentication Methods

#### 3.1 Password-Based Authentication
- **Principle**: Based on "Something you know".
- **Challenges**:
  - Prone to guessing or theft.
  - **Credential Stuffing**: Risk of chain breaches due to users reusing passwords across services.
- **Best Practices**:
  - Use strong, unique passwords.
  - Hash passwords for storage (Never store in plaintext).
  - Rate limit login attempts (Prevent brute-force).
  - Use CAPTCHA to prevent automated attacks.
  - Enable HTTPS to prevent interception.

#### 3.2 Token-Based Authentication (OTP)

![OTP Example](/images/COMPSCI5104/week3/SSE-Lecture3-050.png)
- **Principle**: Based on "Something you have".
- **Types**:
  - **Physical Tokens**: e.g., Bank dongles, Chip cards.
  - **Digital Tokens**: e.g., OTP (One-Time Password).
- **OTP Types**:
  - **HOTP (HMAC-based)**: Counter-based.
  - **TOTP (Time-based)**: Time-window based (usually 30 seconds).

- **Python Implementation Example (using `pyotp`)**:
```python
import pyotp
import time

# 1. Generate key (Usually generated by server and bound to user)
# base32secret3232 is an example key
totp = pyotp.TOTP('base32secret3232')

# 2. Generate current OTP
current_otp = totp.now()
print(f"Current OTP: {current_otp}")

# 3. Verify OTP
# Simulate immediate user input
is_valid = totp.verify(current_otp)
print(f"Verify immediately: {is_valid}") # => True

# Simulate expiry after 30 seconds
# time.sleep(30)
# is_expired = totp.verify(current_otp)
# print(f"Verify after 30s: {is_expired}") # => False
```

#### 3.3 Authenticator Assurance Levels (AAL)

![AAL Levels](/images/COMPSCI5104/week3/SSE-Lecture3-018.png)
- **AAL 1**: Single-Factor Authentication (SFA), e.g., Password only.
- **AAL 2**: Two-Factor Authentication (2FA), e.g., Password + OTP.
- **AAL 3**: Multi-Factor Authentication (MFA) including hardware tokens, for high-security environments.

### 4. Authorization Models

#### 4.1 Discretionary Access Control (DAC)

![DAC Model](/images/COMPSCI5104/week3/SSE-Lecture3-058.png)
- **Core Concept**: The resource **Owner** has the discretion to grant access rights.
- **Implementation**: Typically via **ACLs (Access Control Lists)** (e.g., Windows/Linux file permissions).
- **Pros**: Flexible, easy to use, decentralized management.
- **Cons**:
  - **Low Security**: Vulnerable to "Trojan Horse" attacks (If the Owner is compromised, permissions are abused).
  - Chaotic Management: Hard to maintain as users increase.

#### 4.2 Role-Based Access Control (RBAC)

![RBAC Model](/images/COMPSCI5104/week3/SSE-Lecture3-068.png)
- **Core Concept**: Permissions are assigned to **Roles**, and users acquire permissions by being assigned roles.
- **Relationship**: User -> Role -> Permission.
- **Pros**:
  - **Simplified Management**: No need to configure permissions for each user individually.
  - **High Security**: Follows the Principle of Least Privilege.
  - **Scalable**: Adapts to organizational changes.
- **Cons**: Role definitions can become complex (Role Creep).

#### 4.3 Attribute-Based Access Control (ABAC)
- **Core Concept**: Dynamically decides access based on attributes of User, Resource, Environment (Time, Location), and Policies.
- **Formula**: `Decision = Policy(Subject Attributes, Object Attributes, Environment)`
- **Pros**:
  - **Fine-Grained**: Can enforce rules like "Access allowed only during working hours on intranet".
  - **Dynamic**: No need to pre-define all roles.
- **Cons**: Complex implementation, high policy maintenance cost, potential performance overhead.

#### 4.4 Mandatory Access Control (MAC)

![MAC Model](/images/COMPSCI5104/week3/SSE-Lecture3-078.png)

![MAC Clearances](/images/COMPSCI5104/week3/SSE-Lecture3-079.png)
- **Core Concept**: A central authority mandates policies based on **Security Labels**.
- **Mechanism**: Subjects (Users) have "Clearance", Objects (Files) have "Classification".
- **Rule Example**:
  - **Confidential < Secret < Top Secret**
  - Users can only access content where their Clearance >= File Classification (typically follows Bell-LaPadula "No Read Up, No Write Down").
- **Pros**: Extremely high security, users cannot leak permissions.
- **Cons**: Inflexible, high management cost, mostly used in military/government.



---

## Best Practices & Summary
1. **Preferred Choice**: For most enterprise applications, **RBAC** is the default and best choice, balancing management cost and security.
2. **Fine-Grained Supplement**: If time or location-based control is needed, overlay **ABAC** on top of RBAC.
3. **Security Baseline**:
   - Authentication must be at least AAL2 (Enable 2FA).
   - Password storage must be salted and hashed.
   - Permission assignment follows "Principle of Least Privilege".
