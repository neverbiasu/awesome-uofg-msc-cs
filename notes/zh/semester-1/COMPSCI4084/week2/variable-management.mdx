## 关键知识点

### 局部作用域 vs 全局作用域
- **动机**：理解变量的可见范围与生命周期，避免意外修改全局状态。
- **核心概念**：
  - **局部作用域**：函数内定义的变量，仅在函数内可见，函数返回后销毁
  - **全局作用域**：函数外定义的变量，整个程序可见
  - 函数内修改全局变量需使用 `global` 关键字（不推荐）
  - 参数变量、循环变量也属于局部变量
- **使用场景/模式**：
  - 函数内部计算用局部变量，保持函数独立性
  - 全局常量（配置）用大写命名：`MAX_SIZE = 100`
  - 跨函数传递数据优先用参数和返回值，而非全局变量
- **示例**：
```python
# 局部与全局作用域示例
# 说明：函数内对局部变量的修改不影响全局变量
x = 10  # 全局变量
def modify_local():
    x = 5  # 局部变量，与全局 x 无关
    print(f"Inside function: x = {x}")
modify_local()  # 输出：Inside function: x = 5
print(f"Outside function: x = {x}")  # 输出：Outside function: x = 10
# 使用 global 修改全局变量（不推荐）
# 说明：global 声明后可修改全局变量，但会引入副作用
count = 0  # 全局变量
def increment_global():
    global count  # 声明要修改全局变量
    count += 1
increment_global()
print(count)  # 输出：1（全局 count 被修改）
```
- **注意事项/最佳实践**：
  - 优先使用局部变量，减少全局状态依赖
  - 避免在函数内修改全局变量；如需共享状态，通过参数传递
  - 全局常量用大写加下划线命名（`CONFIG_FILE`），表明不应修改
- **小结**：局部变量仅在函数内可见；修改全局变量需 `global` 声明，但会引入副作用，应尽量避免。

### 什么是副作用（Side Effects）
- **动机**：识别函数对外部状态的修改，理解副作用对程序行为的影响。
- **核心概念**：
  - **副作用**：函数修改了其局部环境之外的状态
  - 常见副作用：
    - 修改全局变量
    - 修改传入的可变参数（如 list、dict）
    - 执行 I/O 操作（打印、文件读写、网络请求）
    - 修改类的实例属性
  - 副作用使程序行为依赖于执行顺序与上下文，增加调试难度
- **使用场景/模式**：
  - 有副作用：修改全局计数器、更新数据库、打印日志
  - 无副作用：纯计算函数、数据转换函数
- **示例**：
```python
# 有副作用的函数
# 说明：函数修改了全局变量 count，产生副作用
count = 0  # 全局变量
def increment():
    global count
    count += 1  # 修改全局状态（副作用）
print(f"Before: {count}")  # 输出：Before: 0
increment()
print(f"After: {count}")   # 输出：After: 1
# 修改可变参数也是副作用
# 说明：函数修改了传入的列表
def append_item(lst, item):
    lst.append(item)  # 修改传入参数（副作用）
numbers = [1, 2, 3]
append_item(numbers, 4)
print(numbers)  # 输出：[1, 2, 3, 4]（原列表被修改）
```
- **注意事项/最佳实践**：
  - 副作用使函数行为不可预测，难以测试与调试
  - 函数命名应反映副作用：如 `update_count()` 而非 `get_count()`
  - 调试时，副作用函数的行为依赖于调用顺序与上下文
- **小结**：副作用是函数对外部状态的修改；识别副作用有助于理解程序行为与调试问题。

### 编写无副作用函数（纯函数模式）
- **动机**：避免副作用，编写可预测、可测试、可复用的函数。
- **核心概念**：
  - **纯函数**：
    - 相同输入总是产生相同输出
    - 不修改外部状态（无副作用）
    - 不依赖外部状态
  - 策略：通过返回值传递结果，而非修改全局变量或参数
  - 函数式编程强调纯函数，提高代码可预测性与可测试性
- **使用场景/模式**：
  - 数据转换：输入 → 处理 → 返回新数据
  - 计算函数：接收参数，返回计算结果
  - 避免修改传入的可变参数，创建副本后修改
- **示例**：
```python
# 无副作用的函数（纯函数）
# 说明：通过返回值传递结果，不修改全局状态
def increment(value):
    return value + 1  # 返回新值，不修改外部状态
count = 0
count = increment(count)  # 通过返回值更新
print(count)  # 输出：1
# 对比：有副作用 vs 无副作用
# 说明：避免修改传入列表，返回新列表
# ❌ 有副作用
def add_item_side_effect(lst, item):
    lst.append(item)  # 修改原列表
    return lst
# ✅ 无副作用
def add_item_pure(lst, item):
    return lst + [item]  # 返回新列表，不修改原列表
numbers = [1, 2, 3]
new_numbers = add_item_pure(numbers, 4)
print(numbers)      # 输出：[1, 2, 3]（原列表未变）
print(new_numbers)  # 输出：[1, 2, 3, 4]（新列表）
```
- **注意事项/最佳实践**：
  - 纯函数易于测试（输入输出固定）与调试（无外部依赖）
  - 不可避免副作用时（如 I/O），将副作用函数与纯函数分离
  - 优先返回新对象而非修改传入对象（尤其是列表、字典）
- **权衡与替代**：
  - 纯函数可能增加内存开销（创建新对象）
  - 性能关键场景可考虑就地修改，但需明确文档说明
- **小结**：纯函数通过返回值传递结果，不修改外部状态；提高代码可预测性与可测试性。

### 变量命名冲突的挑战
- **动机**：避免不同作用域中同名变量引起的混淆与错误。
- **核心概念**：
  - 不同作用域可存在同名变量（局部遮蔽全局）
  - 大型程序或多人协作中，命名冲突增加调试难度
  - 变量遮蔽虽然合法，但可能引起混淆
- **使用场景/模式**：
  - 小型脚本中，偶尔的遮蔽可接受
  - 大型项目或团队协作中，应避免遮蔽与重名
- **示例**：
```python
# 变量命名冲突示例
# 说明：多个同名变量在不同作用域共存，容易混淆
x = 100  # 全局变量
def outer():
    x = 50  # 外层函数局部变量
    def inner():
        x = 10  # 内层函数局部变量
        print(f"Inner x: {x}")
    inner()  # 输出：Inner x: 10
    print(f"Outer x: {x}")  # 输出：Outer x: 50
outer()
print(f"Global x: {x}")  # 输出：Global x: 100
# 调试陷阱
# 说明：意外使用同名变量导致逻辑错误
total = 0  # 全局累加器
def calculate_sum(numbers):
    total = 0  # 局部变量，遮蔽全局 total
    for num in numbers:
        total += num
    return total
result = calculate_sum([1, 2, 3])
print(f"Result: {result}, Global total: {total}")
# 输出：Result: 6, Global total: 0（全局 total 未被修改）
```
- **注意事项/最佳实践**：
  - 使用描述性且唯一的变量名，避免通用名（如 `x`、`temp`、`data`）
  - 团队协作中，遵循命名规范（如前缀区分模块）
  - 函数应短小专注，减少局部变量数量
  - 代码审查时留意同名变量
- **小结**：同名变量可在不同作用域共存，但容易引起混淆；使用描述性唯一命名减少冲突风险。

### Jupyter Notebook 中的变量管理
- **动机**：Jupyter Notebook 允许非线性执行，导致变量状态不一致；理解执行顺序对结果的影响。
- **核心概念**：
  - Notebook 单元格可任意顺序执行，变量状态依赖执行历史
  - 变量在单元格间共享，后执行的单元格可覆盖先前的定义
  - 不按顺序执行可能导致意外结果
  - 内核状态累积，重启内核可清空所有变量
- **使用场景/模式**：
  - 探索性数据分析（频繁修改与重跑单元格）
  - 实验与调试（快速迭代）
- **示例**：
```python
# Jupyter Notebook 变量管理陷阱示例
# 单元格 1（首次执行）
x = 10
print(x)  # 输出：10
# 单元格 2（修改 x）
x = 20
print(x)  # 输出：20
# 单元格 1（再次执行）
x = 10
print(x)  # 输出：10（覆盖单元格 2 的修改）
# 单元格 3（依赖执行顺序）
print(x)  # 输出取决于单元格 1 和 2 的执行顺序！
```
- **注意事项/最佳实践**：
  - **按顺序执行**：从上到下依次运行单元格，避免跳跃
  - **定期重启内核**：`Kernel > Restart & Run All` 确保干净状态
  - **避免隐式依赖**：每个单元格应尽量自包含，减少对前序单元格的依赖
  - **明确变量初始化**：重要变量在首个单元格初始化
  - **使用 `%who` 或 `%whos`**：查看当前所有变量
- **权衡与替代**：
  - 探索阶段可灵活执行，但最终应线性重跑验证
  - 复杂逻辑考虑提取为 `.py` 模块，在 Notebook 中导入
- **小结**：Jupyter Notebook 允许非线性执行，需注意变量状态一致性；按顺序执行与定期重启内核是关键实践。

## 最佳实践
- 优先使用局部变量；需跨函数共享数据时，通过参数传递与返回值，避免全局变量。
- 编写纯函数（无副作用）：相同输入产生相同输出，不修改外部状态。
- 使用描述性且唯一的变量名，避免同名变量引起的混淆（尤其在大型项目中）。
- 函数命名应反映副作用：修改状态用 `update_*`、`set_*`；纯计算用 `get_*`、`calculate_*`。
- Jupyter Notebook 中按顺序执行单元格，定期重启内核验证代码正确性。
- 不可避免副作用时（I/O 操作），将副作用逻辑与纯函数分离，便于测试与维护。
