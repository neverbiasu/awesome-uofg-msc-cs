## 概要

- **目标**：理解现代 Web 应用的系统架构（从单体到多层）、数据管理的重要性以及以用户为中心的信息架构设计方法。
- **范围**：涵盖 Web 应用分类、系统架构模式（Client-Server, N-Tier）、实体关系图（ERD）与 Django 模型映射、以及信息架构的产出物（Site Maps, User Flows, Wireframes）。

## 学习目标

1. **理解** Web 应用的不同类型（静态、交互式、事务型等）及其演变。
2. **掌握** 分层架构（Tiered Architectures）的概念、优势及常见模式（2-Tier, 3-Tier）。
3. **能够** 识别并创建高层系统架构图与实体关系图（ER Diagrams）。
4. **应用** 信息架构原则来开发用户需求、网站地图（Site Maps）、用户流程（User Flows）和线框图（Wireframes）。

## 关键知识点

### 1. Web 应用类型与演变

- **动机**：Web 从最初的静态文档共享演变为复杂的分布式应用系统。理解其分类有助于选择合适的技术栈。
- **核心概念**：
  - **静态 (Static)**：手动构建的 HTML 页面，维护成本高，无服务器端逻辑。
  - **交互式 (Interactive)**：包含表单、菜单，服务器端动态生成页面（如 CGI, PHP）。
  - **事务型 (Transactional)**：涉及数据捕获与数据库存储（如电商结算）。
  - **工作流型 (Workflow-based)**：反映业务流程序列（如酒店预订）。
  - **协作与社交 (Collaborative/Social)**：多用户共享与交互（如 Wiki, Facebook）。
  - **移动与泛在 (Mobile/Ubiquitous)**：跨设备访问与传感器集成。
- **使用场景**：
  - 展示型官网 -> 静态/交互式。
  - 企业业务系统 -> 事务型/工作流型。
- **小结**：Web 应用复杂度随功能需求增加，需采用工程化方法进行架构设计。

---

### 2. 系统架构 (System Architecture)

- **动机**：为了管理复杂性，将系统拆分为职责单一的组件（Component）。架构图是开发团队与客户沟通的蓝图。
- **核心概念**：
  - **单体架构 (Monolithic)**：UI、逻辑、数据存储混杂在一起（如早期的 Java Swing + File I/O）。不适合 Web。
  - **分层架构 (Tiered Architecture)**：将不同关注点分离到不同层级。
    - **2-Tier (Client-Server)**：
      - **Thin Client**: 浏览器只负责渲染 HTML，服务器处理所有逻辑与数据（早期 Web）。
      - **Extended Thin Client**: 客户端通过 CSS/JS 处理部分展示逻辑。
      - **问题**: 客户端负载过重或服务器成为瓶颈；紧耦合。
    - **3-Tier**: 
      - **Presentation Tier (Client)**: 用户界面。
      - **Application Tier (Middleware)**: 业务逻辑、计算、处理（如 Django, App Server）。
      - **Data Tier (Database)**: 数据持久化与管理。
    - **N-Tier**: 进一步拆分应用层，如独立的 Web Server, App Server, Media Server，以及负载均衡（Load Balancing）。
- **示例**：
  ```text
  [Client Browser] <--> [Load Balancer] <--> [Web Server] <--> [App Server (Django)] <--> [Database (MySQL)]
  ```

- **注意事项**：
  - **分离关注点 (Separation of Concerns)**：每层只关注自己的职责。
  - **可伸缩性 (Scalability)**：分层允许在不同机器上部署不同层，通过增加机器（Replication）处理更多负载。
- **小结**：现代 Web 应用通常采用 3-Tier 或 N-Tier 架构，以实现更好的维护性、灵活性和扩展性。

### 3. 数据管理与建模 (Database Modelling)

- **动机**：Web 应用核心在于数据。需要高效的方式存储、检索和管理数据。
- **核心概念**：
  - **ER 模型 (Entity Relationship Model)**：抽象表示数据及其关系。
    - **实体 (Entity)**：矩形（如 User, Product）。
    - **关系 (Relationship)**：菱形（如 Buys, Enrolls）。
    - **属性 (Attribute)**：描述实体的特征（如 Name, Price）。
  - **压缩 Chen 表示法 (Compressed Chen Notation)**：实体与关系在图中，属性单独列表，避免图表过于杂乱。
- **示例**（Django 映射）：
  - 1-to-N: `models.ForeignKey`
  - 1-to-1: `models.OneToOneField`
  - M-to-N: `models.ManyToManyField`
- **使用场景**：设计数据库 Schema 前必须进行建模，以确保数据一致性与完整性。
- **小结**：ER 图是数据库设计的标准工具，可直接映射为 Django Models。

### 4. 信息架构 (Information Architecture, IA)

- **动机**：帮助用户在数字空间中“找到”并“理解”信息。连接用户需求、业务目标与内容。
- **核心概念**：
  - **主要交付物 (Deliverables)**：
    1.  **用户需求 (User Requirements)**：User Stories, Personas, MoSCoW 优先级（Must, Should, Could, Won't）。
    2.  **网站地图 (Site Maps)**：网站的高层结构蓝图，展示页面层级关系。
    3.  **用户流程 (User Flows)**：用户完成特定任务（如“购买商品”）的步骤图。
    4.  **线框图 (Wireframes)**：页面布局草图，展示结构而非视觉设计（低保真）。

![Wireframe Example](/images/COMPSCI5012/L1-IntroSysArchDBInfoArch-080.jpg)

![Flowchart Example](/images/COMPSCI5012/L1-IntroSysArchDBInfoArch-075.jpg)

- **最佳实践**：
  - **URL 设计**：简短、语义化、小写、避免特殊字符（如 `/products/shoes` 优于 `/p?id=123`）。
  - **可访问性 (Accessibility)**：始终为图片提供 `ALT` 文本，考虑残障用户（W3C WCAG 标准）。
- **小结**：IA 是“用户体验设计”的基础，先于编码进行，能有效减少返工。

---

## 最佳实践

- **先设计后编码**：利用架构图、ER 图和线框图在开发前理清思路。
- **保持各层独立**：在系统架构中，确保修改 UI 不会破坏数据库逻辑（通过 API 或 ORM 隔离）。
- **以用户为中心**：使用 Persona 和 User Flows 确保系统功能符合真实用户的使用场景。
- **重视可访问性**：Web 应用应包容所有用户，遵守可访问性标准是职业素养。
