## 概要

- **目标**：理解 Web 开发的复杂性及框架（Frameworks）如何解决这些问题；掌握 MVC 架构及其在 Django 中的变体 MVT；熟悉 Django 的核心组件。
- **范围**：Web 开发工具演变、框架 vs 类库、MVC 模式、Django 设计哲学、Django 核心模块（Models, Views, URLs, Templates）。

## 学习目标

1. **理解** Web 开发的复杂性以及为何需要框架。
2. **区分** 库（Library）与框架（Framework）的区别（控制反转）。
3. **掌握** MVC（Model-View-Controller）架构模式。
4. **理解** Django 的 MVT（Model-View-Template）架构及其请求处理流程。

## 关键知识点

### 1. Web 开发的复杂性与框架

- **动机**：Web 开发涉及多种语言（HTML/CSS/JS/SQL/Python）、不断变化的标准、浏览器兼容性问题以及无状态的 HTTP 协议。手动处理这些问题效率低下且容易出错。
- **核心概念**：
  - **框架 (Framework)**：为特定领域（如 Web）提供设计和部分实现的软件骨架。
  - **控制反转 (Inversion of Control, IoC)**：
    - **库 (Library)**：你的代码调用库。
    - **框架 (Framework)**：框架调用你的代码（你只需填充特定部分）。
  - **特性**：默认行为（Default Behavior）、可扩展性（Extensibility）、不可修改的核心代码。
- **使用场景**：构建中大型 Web 应用时，使用框架可避免重复造轮子（如 Auth, ORM, Session）。
- **小结**：框架通过提供预制组件和架构模式，极大地提高了开发效率和代码质量。

---

### 2. MVC 架构 (Model-View-Controller)

- **动机**：为了降低系统耦合度，将数据、显示和控制逻辑分离。
- **核心概念**：
  - **Model (模型)**：操作应用程序数据（CRUD），定义数据结构。
  - **View (视图)**：展示层，决定数据如何呈现给用户。
  - **Controller (控制器)**：协调者，接收用户输入，操作模型，并选择视图进行显示。
- **优势**：
  - 关注点分离（Separation of Concerns）。
  - 代码复用（Reusable Views/Models）。
  - 易于维护和测试。
- **缺点**：增加了初期开发的复杂度和抽象成本。

---

### 3. Django 与 MVT 架构

- **核心概念**：Django 是一个高层次的 Python Web 框架，鼓励快速开发和清晰的设计。
- **MVT (Model-View-Template)**：Django 对 MVC 的一种实现变体。
  - **Model**：描述数据库结构（同 MVC）。
  - **View**：决定**显示什么**数据（业务逻辑）。相当于 MVC 中的 Controller（部分）+ View（逻辑）。
  - **Template**：决定**如何显示**数据（HTML 呈现）。相当于 MVC 中的 View（呈现）。
  - **Controller**：由 Django 框架本身和 URL 解析器（URL Parser）处理。

![Django Architecture Detail](/images/COMPSCI5012/L2-WAFsDjango-068.jpg)

- **核心组件**：
  - **models.py**：定义数据库实体和关系（ORM）。
  - **views.py**：处理请求，获取数据，渲染模板。
  - **urls.py**：URL 路由，将 URL 映射到 View 函数。
  - **templates/**：HTML 文件，包含展示逻辑。

- **请求处理流程**：
  1. 用户请求 URL。
  2. `urls.py` 解析 URL 并匹配到相应的 View。
  3. View 处理逻辑，可能从 `models.py` 获取数据。
  4. View 将数据传递给 `template` 进行渲染。
  5. 返回 HTTP 响应给用户。

- **小结**：Django 通过 MVT 架构实现了业务逻辑与表现层的分离，并内置了 Admin、Auth 等强大功能，适合快速构建复杂的数据驱动型网站。

---

### 4. 框架对比 (Django vs Flask vs Rails)

- **Django**: "Batteries included"（全家桶），内置 ORM、Admin、Auth。适合大型应用，规范性强。
- **Flask**: 微框架（Microframework），核心极简，按需添加扩展。适合小型应用或 API，灵活性高。
  
  ![Flask Logo](/images/COMPSCI5012/L2-WAFsDjango-083.png)

- **Ruby on Rails**: 约定优于配置（Convention over Configuration），开发极快，但“魔法”较多。

  ![Rails Architecture](/images/COMPSCI5012/L2-WAFsDjango-077.png)

- **选择建议**：根据项目规模、团队熟悉度及特定需求选择。

## 最佳实践

- **利用 IDE**：使用 PyCharm 或 VS Code 等 IDE，利用其代码补全和调试功能。
- **遵循 DRY 原则**：Don't Repeat Yourself，利用 Django 的模板继承和组件复用。
- **使用虚拟环境**：每个 Django 项目都应运行在独立的 Python 虚拟环境中。
- **保持 View 简洁**：业务逻辑尽量放在 Model 或 Service 层，View 只负责处理请求和响应。
