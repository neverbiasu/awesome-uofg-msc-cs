# 分布式系统中的计算挑战

当计算扩展到多台机器时，我们面临许多单机环境中不存在的挑战。理解这些挑战对于设计有效的大数据解决方案至关重要。

## 为什么分布式计算很难

### 单机 vs 分布式

| 方面 | 单机 | 分布式系统 |
|------|------|-----------|
| 故障 | 罕见，全局性 | 常见，局部性 |
| 通信 | 纳秒级（内存） | 毫秒级（网络） |
| 一致性 | 保证 | 需要管理 |
| 调试 | 直接 | 复杂 |

<Callout type="info">
在分布式系统中，任何可能出错的事情都会出错——而且是在最糟糕的时候。
</Callout>

## 关键挑战

### 1. 容错

在大型集群中，硬件故障是常态，而非例外。

**故障统计**：
- Google报告每年约1-5%的磁盘故障率
- 在大规模（10,000+机器）时，预计每天有多次故障
- 网络分区经常发生

**故障类型**：
- **硬件**：磁盘、内存、CPU、电源
- **软件**：Bug、崩溃、内存泄漏
- **网络**：分区、丢包、延迟峰值
- **人为**：配置错误、意外删除

**解决方案**：
- 数据和计算的复制
- 检查点保存中间结果
- 自动任务重新执行
- 优雅降级

### 2. 数据局部性

移动数据很昂贵；移动计算更便宜。

**问题所在**：
```
网络带宽 << 磁盘带宽 << 内存带宽
```

| 介质 | 典型带宽 |
|------|----------|
| 网络 (1Gbps) | ~100 MB/s |
| 磁盘 (HDD) | ~100-200 MB/s |
| SSD | ~500-3000 MB/s |
| 内存 | ~50,000 MB/s |

**原则**：将计算移动到数据所在位置，而不是相反。

**数据局部性级别**：
1. **进程本地**：数据在同一进程内存中
2. **节点本地**：数据在同一机器的磁盘上
3. **机架本地**：数据在同一网络机架上
4. **跨机架**：数据在不同机架上

### 3. 同步

跨机器协调工作很复杂。

**挑战**：
- 没有全局时钟
- 消息延迟不可预测
- 部分故障使协调复杂化
- 死锁和竞态条件

**同步模式**：

| 模式 | 描述 | 用例 |
|------|------|------|
| 屏障 | 所有任务等待直到每个人都到达某点 | 迭代算法 |
| 锁 | 共享资源的互斥 | 并发更新 |
| 共识 | 对一个值达成一致 | 领导者选举 |

### 4. 负载均衡

在机器间均匀分配工作。

**落后者问题**：
- 某些任务比其他任务花费更长时间
- 一个慢任务延迟整个作业完成
- 原因：数据倾斜、硬件问题、资源竞争

**解决方案**：
- 推测执行（运行重复任务）
- 细粒度任务划分
- 动态工作窃取
- 数据预处理以减少倾斜

### 5. 网络瓶颈

网络通常是限制因素。

**Shuffle问题**：
- 当数据需要在阶段之间移动时
- N台机器发送到N台机器 = N²连接
- 网络拥塞、丢包

**缓解策略**：
- Combiner（shuffle前的本地聚合）
- 压缩
- 智能分区
- 最小化数据移动

## 编程复杂性

### 传统并行编程

```java
// 手动线程管理
Thread[] threads = new Thread[numWorkers];
for (int i = 0; i < numWorkers; i++) {
    threads[i] = new Thread(() -> {
        // 处理故障？
        // 与其他人协调？
        // 如果这个节点死了怎么办？
    });
    threads[i].start();
}
// 等待所有... 但如果一个崩溃了怎么办？
```

**问题**：
- 显式线程/进程管理
- 手动同步（锁、屏障）
- 复杂的故障处理
- 难以调试和测试

### 我们需要什么

一个编程模型能够：
- 隐藏分布式复杂性
- 自动处理故障
- 透明扩展
- 易于编程

<Callout type="info">
这正是MapReduce提供的——一个简单的编程模型，抽象了分布式计算的复杂性。
</Callout>

## CAP定理

在分布式系统中，你只能保证三个属性中的两个：

| 属性 | 描述 |
|------|------|
| **一致性** | 所有节点看到相同的数据 |
| **可用性** | 系统响应所有请求 |
| **分区容错** | 系统在网络故障时仍能工作 |

**实践中**：
- 网络分区是不可避免的
- 必须在一致性和可用性之间选择
- 不同系统做出不同权衡

| 系统类型 | 选择 | 示例 |
|----------|------|------|
| CP | 一致性优先于可用性 | HBase, MongoDB |
| AP | 可用性优先于一致性 | Cassandra, DynamoDB |

## 总结

| 挑战 | 描述 | 解决方法 |
|------|------|----------|
| 容错 | 机器频繁故障 | 复制、检查点 |
| 数据局部性 | 网络慢 | 将计算移到数据处 |
| 同步 | 没有全局时钟 | 屏障、分布式共识 |
| 负载均衡 | 工作分配不均 | 推测执行、细粒度任务 |
| 网络 | 带宽有限 | 减少数据移动 |
