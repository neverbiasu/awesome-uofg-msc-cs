## 核心要点
软件分析将安全性从手动的“猜谜游戏”转变为系统的验证过程，使用自动化工具检测已知漏洞模式（如缓冲区溢出和数据泄露）。

## 1. 静态应用安全测试 (SAST)
在**不执行程序**的情况下分析代码。
-   **控制流分析**：理解代码可能执行的路径。
-   **数据流分析**：跟踪不受信任的输入（Sinks 和 Sources）。
-   **污点分析 (Taint Analysis)**：识别“被污染的”（用户控制的）数据是否到达了敏感的“接收点 (Sink)”（例如：`SQL.execute()`）。
![污点分析逻辑](/images/COMPSCI5104/week4/SSE-Lecture4-007.png)

## 2. 动态应用安全测试 (DAST)
分析**运行中的应用程序**。
-   **模糊测试 (Fuzzing)**：提供随机、无效或意外的数据作为输入，以寻找崩溃或内存泄漏。
-   **渗透测试**：模拟针对真实系统的真实攻击。

## 3. SAST 与 DAST 的对比
| 特性 | SAST | DAST |
| : | :--- |
| **阶段** | 早期（开发期） | 后期（测试/生产期） |
| **可见性** | 白盒（源代码） | 黑盒（行为） |
| **假正例 (误报)** | 高 | 低 |
| **根因分析** | 识别具体的代码行 | 识别可观察的行为 |

## 4. 出卷人视角：技术细微差别

### 健壮性 (Soundness) vs. 完整性 (Completeness)
-   **健壮性**：如果工具说代码是安全的，那么它确实是安全的（无假负例/漏报）。
-   **完整性**：如果存在 Bug，工具一定能找到它（无假正例/误报）。
-   **细微差别**：在实践中，工具会在两者之间进行权衡。大多数安全工具既不是完美的健壮，也不是完美的完整。

### 硬核红线：假负例 (False Negatives)
-   “假负例”（漏报真实 Bug）比“假正例”（误报安全代码）危险得多。安全分析应优先考虑高召回率 (Recall)。
